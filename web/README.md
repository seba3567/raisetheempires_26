# web/ — la puerta pública

Servicio **Bun + TypeScript** de Raise the Empires. Es lo que el jugador ve: la
landing, las cuentas, los amigos y el progreso. Todo lo demás — el cliente SWF y
el gateway AMF0 — lo sirve el servidor Python, al que este proceso hace de proxy.

```
navegador ──► web/ (Bun, :8080)  ──► empires-server.py (Flask, 127.0.0.1:5005)
              landing, cuentas,        /ruffle.html, /assets, /js,
              amigos, progreso         /flashservices/gateway.php  (AMF0)
```

## Por qué el gateway sigue en Python

El SWF habla AMF0 y el dialecto exacto que produce `pyamf` es un contrato: los
arrays densos frente a los objetos con claves numéricas, y los marcadores de
referencia. Ruffle no implementa `AmfValue::Reference`, así que un solo objeto
serializado dos veces rompe el cliente. El cliente no tiene código fuente, así
que no se puede recompilar para tolerar otra codificación. **El códec no se
reescribe, se protege.**

La consecuencia práctica: `empires-server.py` nunca se expone a internet. Este
servicio es su única puerta, y por eso el dev server de Flask no necesita ser
production-ready.

## Por qué `zid` se deriva de la cuenta

El servidor Python asigna la identidad del jugador a partir de la cookie de
sesión:

```python
zid = crc64_go_iso(session_id) // 2048
```

Una cookie se regenera. Cuando eso pasa, el mismo jugador recibe otro `zid` y su
partida queda partida en dos. Aquí el `zid` se deriva del **id de la cuenta**,
que no cambia al cerrar sesión, cambiar la contraseña ni rotar la cookie.

`src/ids.ts` es el port de `crc64_go_iso.py` y `tests/ids.test.ts` fija los
mismos vectores que el test de Python, así que ambos lenguajes producen el mismo
valor. La división por 2048 no es estética: ActionScript 3 no tiene enteros,
todo `Number` es un `double`, y el checksum de 64 bits no cabría exacto.

## La base de datos

SQLite vía `bun:sqlite`: cero dependencias externas, un archivo, coherente con el
carácter de preservación del proyecto. Todo el SQL vive en `src/db/` y usa un
dialecto portátil, así que cambiar a Postgres es un driver nuevo detrás de
`client.ts`, no una reescritura de las consultas. Dos cosas que hay que tocar al
hacerlo:

- `client.ts` — los placeholders pasan de `?` a `$1`.
- `001_init.sql` — `INTEGER PRIMARY KEY` debe pasar a
  `GENERATED BY DEFAULT AS IDENTITY`.

Postgres antes que MariaDB: JSONB para el progreso, despliegue con un contenedor,
y es lo que vas a encontrar en cualquier hosting moderno.

## Arrancar

```powershell
cd web
bun install

# La clave que firma la sesión. Obligatoria.
bun -e "console.log(crypto.randomUUID()+crypto.randomUUID())"
# -> ponerlo en web/.env (copiar de .env.example)

bun run start          # :8080
```

En otra terminal, el gateway:

```powershell
..\.venv\Scripts\python.exe empires-server.py --port 5005 --no-popup
```

## Cuentas de administrador

```powershell
$env:ADMIN_USER="tu_usuario"
$env:ADMIN_PASS="tu_password"
bun run scripts/manage-user.ts create-admin

bun run scripts/manage-user.ts list-admins
bun run scripts/manage-user.ts promote <usuario>
bun run scripts/manage-user.ts demote  <usuario>
bun run scripts/manage-user.ts delete  <usuario>
```

La contraseña se lee del entorno, nunca de un argumento, para que no quede en el
historial de la shell ni en un log. El último admin no se puede degradar ni
borrar.

## El editor de imperio es solo de admins

El gateway es más viejo que las cuentas: `/gazillionaire`, `/patch/...` y
`/save-editor`reachable para cualquiera con una sesión de juego, y `/list_session`
entrega el session id de todos los jugadores. Con cuentas reales, el chequeo de
rol va en `src/access.ts`, que es la única capa que sabe quién está conectado.

| Ruta | Qué hace |
| --- | --- |
| `/save-editor` | Editor de imperio: recursos, nivel, quests, editor raw |
| `/gazillionaire` | +10.000 Empire Points |
| `/deprogress` | Rebobina el progreso |
| `/patch/…` | Parchea cualquier campo del save |
| `/seed/…`, `/unlock_quest/…`, `/complete_quest/…`, `/remove_quest/…` | manipulating quests |
| `/list_session` | Lista todas las sesiones guardadas |
| `/language_editor` | Editor de traducciones |

Sin sesión: **401**. Con cuenta normal: **403**, y la respuesta no dice qué hay
detrás del muro. Con `role = admin`: pasa al gateway tal cual.

El criterio es estrecho a propósito: se cierra lo que cambia el estado del juego
o expone datos de otro jugador, y se deja todo lo demás. Una lista negra
amplia sobre las rutas del gateway rompería al cliente la primera vez que pide una
ruta que nadie pensó en permitir.

> **Esto solo funciona si Flask sigue en loopback.** El candado está en Bun, no
> en Python. Si expones `empires-server.py` en `0.0.0.0`, cualquiera alcanza el
> editor saltándoselo por completo. El servicio de Bun es la única puerta, y
> `--host` del gateway debería quedar en `127.0.0.1`.

### El detalle que rompe el juego si se toca

`templates/ruffle.html` renderiza `app_url={{ request.host_url }}` en los
FlashVars, y el cliente arma su URL del gateway a partir de ahí
(`Config.SERVICES_GATEWAY_PATH`). Flask tiene que ver el host **público**. Si el
proxy no reenvía `Host`, Flask ve `127.0.0.1:5005`, el `app_url` apunta al
gateway directo y el juego se salta este servicio por completo — en silencio, sin
ningún error visible. Hay un test que lo fija:
`tests/proxy.test.ts` → "gives Flask the PUBLIC host, not the upstream address".

### Y el detalle que lo deja en pantalla negra

`fetch` de Bun **decodifica el body**: infla un `gzip` y devuelve bytes planos,
pero deja el header `Content-Encoding: gzip` en la respuesta. Si el proxy reenvía
ese header, el navegador intenta descomprimir texto que ya es texto y la página
muere con `ERR_CONTENT_DECODING_FAILED`. Sin otros síntomas: pantalla negra.

Por eso `proxy.ts` distingue los headers de petición de los de respuesta. En la
respuesta se descartan `content-encoding` y `content-length`; en la petición se
reenvían, porque el body de la petición sí viaja tal cual.

**Consecuencia:** a través del proxy el juego se sirve **sin comprimir**. En
localhost da igual, pero para un despliegue público conviene recomprimir
selectivamente (solo texto/xml/json/js/css por encima de cierto tamaño, nunca lo
que ya venía codificado). Está pendiente a propósito: meter una segunda capa de
codificación sin poder medir la latencia real sería cambiar un fallo visible por
uno invisible.
